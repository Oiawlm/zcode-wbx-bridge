# glm-prompt-crafter — GLM/ZCode 执行提示词工艺库

> **定位**：给 GLM-5.3 / GLM-5.3-Flash 主模型（执行窗口，常用目标模式 /goal）写提示词的完整工艺：
> 受众矩阵定规范 → 工作流定顺序 → 四段式定单条 prompt → 骨架定交接文件 → 子代理要点定委派 →
> 反模式守底线；模型事实与 /goal 机制细节在 references/ 按需读。
> **自包含**：本库不依赖任何项目私有文件，官方出处全部在 references/official-sources.md。
> **三条硬规则贯穿全库**：① 交接提示词自包含——上下文只经文件传递，冷启动无法复原的信息等于没写；
> ② 临时指令写进 prompt，长期规则写入项目级配置（AGENTS.md）；③ 提示词文件自带行数预算，超了先删冗余再补新内容。
> 日期：2026-10-13（v2）　行数预算：≤300 行

## 一、何时用我（三类受众矩阵）

| 受众 | 载体 | 用本库哪部分 |
|---|---|---|
| 规划窗口 → 执行窗口交接 | GOAL 执行提示词文件（如 GOAL-V\<n\>-PROMPT.md） | §四 骨架 + §三 契约 + references/goal-mode-writing.md |
| ZCode 内部子代理 | Agent 工具的 prompt 参数 | §五 要点 + §三 契约 |
| 外部 worker 派发 | ask/fanout 类桥接命令 | 不在本库范围：项目装有派发 skill（如本机 wb-bridge）则用其规范；没有则按 §三 四段式 + 自包含原则写（输入全部打包进提示词、输出可独立校验） |

三条使用规则：

- 三类受众的规范不同，**不得互相套用**（例：不要把 §四 的窗口契约塞进子代理 prompt）。
- 动笔前先把任务归位到上表某一行，再选对应规范；归不了位说明需求本身没想清，先回去澄清。
- 规划窗口的最终输出物 = 供执行窗口执行的提示词文件（落盘），不是对话里的口头交代。

## 二、工作流（五步）

1. **定受众与目标模型**：对照 §一矩阵归位（窗口交接 / 子代理 / 外部 worker）。定目标模型：用户当次明示优先；未明示默认 GLM-5.3（2026-10-13 用户定案）；视觉输入任务不设默认路由，按当次指定——两型模态与读图链路事实见 references/glm-model-profiles.md。
2. **选参考**：按 §六参考地图取材料——涉模型参数与模态 → glm-model-profiles.md；写 /goal 目标 → goal-mode-writing.md；核对出处 → official-sources.md。
3. **按契约写**：单条 prompt 按 §三 四段式；交接文件按 §四 骨架。
4. **过清单**：各章 ☐ 检查点逐个过，§七 反模式逐条排除。
5. **交付**：落盘为文件（命名与文件头规范见 §四.2），给路径不给「正文粘贴」。

## 三、四段式契约（单条提示词的最小充分结构）

出处：智谱官方「Coding Agent 最佳实践」任务描述四要素——目标 → 上下文 → 约束 → 完成标准
（references/official-sources.md §4.1）。结构化输入的作用是**减少模型的猜测空间**：四段残缺时模型只能自行补全，猜测空间随之增大。

### 3.1 目标（Goal）——要实现什么

- 写什么：一句话说清「要实现什么」，结果导向、可验收，不写实现步骤。
- ✅ 正例：「新建 docs/api.md，覆盖全部公开端点，总长 ≤150 行。」
- ❌ 反例：「优化一下文档相关的东西。」——无对象、无边界、无法验收。
- ☐ 检查点：目标里能直接看出交付物文件名或明确产物形态吗？

### 3.2 上下文（Context）——涉及哪些文件/模块

- 写什么：涉及哪些文件/模块；引用文件路径或贴关键片段，含「禁读/别动」清单，让执行者不必猜。
- ✅ 正例：「事实来源为 research/models.md §3，逐条落实，不新增事实。」
- ❌ 反例：「参考之前那个调研。」——依赖会话记忆，新窗口无法复原。
- ☐ 检查点：上下文里每个引用都是可打开的文件路径或可定位的片段吗？

### 3.3 约束（Constraints）——不许做什么

- 写什么：代码风格/架构规则/安全/依赖限制/不动清单（冻结项、禁改文件）。
- ✅ 正例：「不动清单：配置文件只增一节；本轮不改版本号与变更日志。」
- ❌ 反例：「注意别改坏东西。」——把约束写成态度，不构成可执行限制。
- ☐ 检查点：约束明确列出「不许做什么」了吗，而不只是鼓励做什么？

### 3.4 完成标准（Done when）——何时算完成

- 写什么：可判定的完成口径，如测试通过、行为变化、bug 不再复现、行数与格式达标。执行窗口跑目标模式（/goal）时，完成判据必须含校验器可核对的证据（命令/阈值/文件），写法详见 references/goal-mode-writing.md。
- ✅ 正例：「Done when：六节齐全；总长 ≤220 行；每条事实可回溯到材料。」
- ❌ 反例：「做完给我看看。」——没有判定条件，验收必然扯皮。
- ☐ 检查点：第三方不问作者，能否独立判定通过/不通过？

## 四、执行窗口交接提示词骨架（GOAL 文件标准结构）

执行窗口通常以目标模式（/goal）工作：完成判定由独立校验器执行、只认可核对的实据、未达成自动开下一轮
（机制详见 references/goal-mode-writing.md）。骨架因此按「每一段都为最终的可核对验收服务」设计。
执行窗口未开目标模式时同一骨架仍适用，差异仅在验收判据的核对主体与档位建议（见 references/goal-mode-writing.md §五）。

| 段 | 作用 | 写作要点 |
|---|---|---|
| 身份与工作方式 | 声明执行窗口是谁、以什么模式工作 | 产出文件与落地改动，不产出讨论；声明目标模型与工作模式（/goal 开/关）；声明工作铁律（如第一性原理、三原则） |
| 上下文承接指令 | 规定读什么、禁读什么 | 冷启动固定顺序（项目指令 → 路由 → 记忆 → 按角色选读）；禁止无目的通读素材目录，防上下文膨胀推高幻觉率 |
| 背景 | 为什么做本轮工作 | 取自调研底稿的结论（含根因），使执行者能判断边界外情况 |
| Phase 任务 | 把复杂需求拆成可逐步完成的阶段 | 逐 Phase 写清产出物与前置依赖（Plan 先于实现）；边界清单：允许/禁止各一段 |
| 铁律 | 不可协商的行为底线 | 如：外包结果校验后使用、单一写者、冻结项不动、凭证不入提示词 |
| 验收清单 | 汇总可勾选的 Done when | 对齐 §三 四段式，逐条可判定；**目标模式（/goal）下完成判据必须含校验器可核对的证据**（认可/不认可实据清单见 references/goal-mode-writing.md §二） |
| 收尾动作 | 交代落地后的文件维护 | 更新记忆/路由/规划文档、归档留痕、提交推送口径 |

**自包含原则**：每份交接提示词必须自包含——执行窗口不依赖规划窗口的会话记忆，上下文只经文件传递。

### 4.1 文件规范（通用部分）

- 交接资产命名惯例（示例，同工作流项目可沿用）：`GOAL-V<n>-PROMPT.md`（执行提示词）、`RESEARCH-V<n>.md`（调研底稿）——执行提示词以调研底稿为唯一事实源。
- 新 MD 一律三要素：文件头一句话定位 + 来源链接 + 日期；UTF-8 编码；行数预算写进文件头。
- 提示词文件自身也要瘦身：超出行数预算先删冗余，再补新内容。
- 项目内目录语义与读取路由由项目自己的路由文件定义；提示词引用路径前先核对目标文件存在，不引用没有把握的路径。

## 五、子代理提示词要点（ZCode 内部子代理）

- 四要点必写：**自包含**（子代理看不到主上下文，全部输入要打包进 prompt）+ **第一性原理要求** + **期望产出形态** + **只回传结论**（探索过程留在子代理侧，不灌回主上下文）。
- 大批量委派层级 ≤2（主 Agent → 子代理；子代理不再开子代理），避免上下文碎裂与协调成本。
- 命名：同名 skill 第一个赢（用户级遮蔽工作区；发现顺序见 references/official-sources.md §4.3）；批量子代理建议用唯一前缀区分命名。
- 规则不重复抄：AGENTS.md 已注入的规则无需在子代理 prompt 里复述（用户级先注入、工作区后注入可收窄/覆盖）。
- ✅ 正例：「探索 src/ 下全部 MD 的引用关系，只回传：文件清单 + 每文件被引次数 + 死链列表。」
- ❌ 反例：「帮我看看 src 目录。」——无交付物形态、无边界，回传内容会灌满主上下文。
- ☐ 检查点：子代理 prompt 是否声明了第一性原理要求、产出形态、回传边界三件事？

## 七、反模式清单

1. **无 Done when 的模糊任务**：执行者只能靠猜，验收无口径、必然返工。正解：§三 四段式写全，完成标准可第三方判定。
2. **把长期规则写进一次性 prompt**：规则随会话关闭丢失、反复重述、逐步漂移。正解：写入项目级配置（AGENTS.md）。
3. **指令与经验混写一个文件**：经验性信息持续污染系统规则。正解：指令型进 AGENTS.md，学习型进 MEMORY 类记忆文件。
4. **交接提示词不自包含**：执行窗口依赖规划窗口会话记忆，冷启动即断链。正解：上下文只经文件传递。
5. **子代理提示词不声明第一性原理与产出形态**：回传不可用，主上下文被过程灌满。正解：§五 四要点写全，只回传结论。
6. **全量灌上下文代替路由**：上下文膨胀直接推高幻觉率。正解：项目指令 → 路由 → 按角色选读，素材用 grep 定位。
7. **素材目录无目的通读**：同样是上下文膨胀来源。正解：守文档地图「何时读/何时别读」与冷启动硬预算。
8. **同一文件多写者并发**：互相覆盖、内容静默丢失。正解：单一写者铁律，交接以文件为唯一介质。
9. **规范文件自身无行数预算**：规范层膨胀，反成新的上下文负担。正解：行数预算写进文件头，超了先瘦身。
10. **把按需知识塞进常驻注入**（AGENTS.md / 系统提示词）：注入约百行后规则降格为建议、出现大量死重、深层约束被安静忽略（社区多帖实证）。正解：严格规则进配置/hooks，按需知识进 skill 按需加载——本库以 skill 形态存在正是这条反模式的反面。
11. **触发描述泛化导致永不触发**：description 写得笼统，模型永远想不到调用。正解：触发词前载 description、写清 when to use、名字自解释；必要时 `$技能名` 强制兜底。
12. **同一知识多副本并存靠人工同步**：副本漂移是腐化之源。正解：单一事实来源——迁移后删除旧副本、活引用改指新址（本库取代项目内旧版指南即按此原则执行）。
