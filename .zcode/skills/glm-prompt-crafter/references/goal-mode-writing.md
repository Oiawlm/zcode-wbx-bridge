# 目标模式（/goal）提示词写法

> **一句话定位**：给执行窗口写目标模式目标描述的工艺——核心是把**能被独立校验器核对的完成证据**（命令、阈值、文件）写进目标，其余一切（计划、待办、耗时、结论式回复）都不构成完成依据。
> **来源**：全部机制事实出自 ZCode 官方文档 `zcode.z.ai/cn/docs/goal`（2026-10-10 访问，一手）；各节末尾标注来源行。材料未覆盖处标 UNKNOWN 并一行说明，不臆测。
> **日期**：2026-10-10（v1）

## 一、机制速览

### 1.1 命令族

| 命令 | 作用 |
|---|---|
| `/goal <目标描述>` | 开启目标模式并设定目标 |
| `/goal` | 查看当前目标 |
| `/goal replace` | 替换当前目标 |
| `/goal pause` / `/goal resume` | 暂停 / 恢复目标推进 |
| `/goal clear` | 清除当前目标 |

### 1.2 三条会话级约束（写目标前必须知道）

1. **单会话单目标**：一个会话同时只有一个目标。
2. **会话级持久化**：重进会话目标还在、可续跑。
3. **两处设不了目标**：计划模式下、任务运行中都无法设定目标。

（以上来源：zcode.z.ai/cn/docs/goal，2026-10-10）

→ 动笔含义：目标要写成「一个会话能从头跑到尾」的**单一目标**，不是一串并列任务；中途改方向用 `/goal replace`，不是新开一个。

## 二、校验器驱动的核心认知

### 2.1 完成判定由独立校验器负责

- 每轮结束**单独校验一次**；判定未达成即**自动开下一轮**继续推进。
- 校验器不看你「说了什么」，只看**能核对的东西**。

### 2.2 只认可核对的实据

**认可**：改出来的文件；命令输出；测试结果。
**不认可**：计划；待办（todo）；耗时；「听起来像结论的回复」。

→ 动笔含义：在目标里直接点名会产出**哪种实据**（哪个文件、哪条命令、哪项测试/阈值），校验器才有得核。

### 2.3 有待办未完成不判完成

只要还有未完成的待办，校验器就不判完成。

→ 动笔含义：目标里不要留「以后再说」的悬空项——要么写进目标一次做完，要么别列。

### 2.4 三种停止条件

目标推进只在这三种情况下停下：① 校验器判定完成；② 用户暂停或清除（`/goal pause|clear`）；③ 达到用量上限。

> UNKNOWN：「用量上限」的阈值、计费口径与配置入口，官方文档未给出，无法据此说明如何调整。

（§二来源：zcode.z.ai/cn/docs/goal，2026-10-10）

## 三、写法铁则

每条给出「官方要求 → 正反例 → 动笔自检」。

### 铁则 1：目标越具体、越可校验，每轮判断越准

官方原话：「目标描述越具体、越可校验，每轮的判断就越准」。

- ❌ 反例：`优化一下性能`
- ✅ 正例：`把 pnpm test 跑通，并且首屏加载控制在 2 秒内`（官方原例）

自检：把目标读给「只认实据」的校验器听，它能不能立刻知道要核对什么？不能，就再具体一档。

### 铁则 2：把可核对的完成证据（命令、阈值）写进目标

官方要求把可核对的完成证据（命令、阈值）直接写进目标。

- ❌ 反例：`让登录流程更稳一点`
- ✅ 正例：`跑通 npm run test:e2e -- login，且输出 0 failing`（按官方「命令+阈值」要求改写，命令名/阈值按项目替换）

自检：目标里至少出现一条**真跑得出输出的命令**或一个**可比较的阈值**（数字、退出码、通过/失败）。

### 铁则 3：认准适合目标模式的任务画像

官方画像：「一句话说得清、但要多轮才能做完的活」。

- 适合：一句话能描述、需多轮迭代的活（按铁则 1、2 写）。
- 不适合：单轮即成的琐事（直接普通提示词）；「一句话说不清」的模糊大工程（先拆到一个能说清的目标再用 `/goal`）。

自检：能否一句话讲清「做完时世界长什么样」？能、且需要多轮 → 用目标模式。

### 铁则 4：长任务配完全访问 / 自动编辑档

官方建议长任务配完全访问 / 自动编辑档，避免每轮卡在人工确认上。

> UNKNOWN：该档位的具体名称与开关入口，官方文档未给出，以客户端实际设置项为准。

（§三来源：zcode.z.ai/cn/docs/goal，2026-10-10）

## 四、最小可用的 /goal 目标描述骨架模板

围绕「单目标、可多轮、可被实据校验」三条约束：

```text
/goal 把 <产物/模块> 做到 <可核对的结果>：
1) 完成证据：运行 `<命令>`，达到 <阈值/退出码/通过标准>；
2) 产物落点：产出/修改 <文件路径>；
3) 判定口径：以第 1 条命令输出与第 2 条文件为唯一完成依据；
   计划、待办、耗时、结论式回复不作为完成依据；
4) 边界：本目标仅此一项，做到即停；过程中不留未完成待办。
```

占位符填写要点：

| 占位符 | 填写要点 |
|---|---|
| `<产物/模块>` | 一句话说清「做什么」，对应「一句话说得清」画像 |
| `<可核对的结果>` | 描述做完时世界的样子，而非动作意图 |
| `<命令>` | 一条能真跑、有输出的命令 |
| `<阈值/退出码/通过标准>` | 可比较的数字或通过条件（如「0 failing」「≤2s」） |
| `<文件路径>` | 校验器可核对的产物落点 |
| 第 3 条 | 显式声明只认实据，复述不认可清单 |
| 第 4 条 | 单会话单目标 + 不留未完成待办 |

使用步骤：① 复制模板填入占位符；② 按第三章四条铁则逐条自检（够具体？含命令/阈值？画像对得上？长任务已调档？）；③ `/goal <目标描述>` 下发；查看用 `/goal`，改向用 `/goal replace`。

（§四来源：zcode.z.ai/cn/docs/goal 的机制事实组装，2026-10-10）
